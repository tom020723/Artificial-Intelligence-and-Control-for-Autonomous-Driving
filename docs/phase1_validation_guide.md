# Phase 1 재학습 및 검증 가이드

작성일: 2026-11-16. 대상: `parallel_train` 브랜치.
작성 시 코드 커밋: `fae3f3fc90d24bc0538732760bc189339bc0760d`.

## 1. 달성할 목표와 범위

**동일한 학습 설정으로 seed 0·1·2를 각각 무작위 초기화부터 새로 학습하고, 세 모델 모두 Phase 1 기준을 충족하는지 판정한다.** 기존 seed 0 모델로 새 seed 0 학습을 대체하지 않는다.

여기서 Phase 1은 신호등 정상 작동, 배경 차량 없음이다. 랜덤 출발 차선을 포함한다. 과거 `train.md`의 전체 청신호 Phase 1과 구분한다.

수행 순서는 평가 도구 준비 → 설정 동결 → seed 0 학습·평가 → seed 1 학습·평가 → seed 2 학습·평가 → 통합 보고서 작성이다. 실패도 실험 결과이므로, 성능 미달을 숨기거나 통과 모델만 골라 보고하지 않는다.

이 문서는 실행 지침이다. 문서 작성 시점에 새 학습이나 검증을 실행했다는 의미는 아니다.

## 3. 긴 학습 전에 평가 도구 준비

현재 `scripts/evaluate_quick.py`는 기본 신호 시점 평가와 A2 Ring 출발 차선 sweep을 지원한다. `--offset-set`, `--output-dir` 옵션 및 별도 trace 스크립트는 현재 없다. 없는 옵션을 실행하거나 지원한다고 보고하지 않는다.

다음 최소 확장을 먼저 완료한다. 학습 환경·정책·보상 계산은 수정하지 않는다.

1. `evaluate_quick.py`에 `--offset-set development|holdout`을 추가한다.
   - development: ticks `range(2, 250, 5)`, 시각 1.0, 3.5, …, 123.5초.
   - holdout: ticks `range(4, 250, 5)`, 시각 2.0, 4.5, …, 124.5초.
   - tick당 0.5초이며, 각 세트는 50개다. 기존 기본 동작은 유지한다.
   - 각 세트의 실제 ticks가 worker 입력, 그래프, 요약 JSON에 모두 일관되게 적용되어야 한다.
   - development 출력은 `analysis/quick/`, holdout은 `analysis/quick_holdout/`으로 분리한다.
2. 출발 차선 평가 난수를 신호 tick과 분리한다. 같은 경로·offset 순번은 세 모델 및 두 세트에서 같은 출발 차선을 사용하도록 episode seed를 고정된 평가 seed·경로 인덱스·offset 순번으로 만든다. 평가 seed에 학습 seed를 사용하지 않는다. 실제 `start_lane`의 일치 여부를 결과 CSV로 확인한다.
3. CSV의 `(route, signal_offset_s)` 조합이 세트당 1,150개이며 중복·누락이 없는지 검사한다. 경로는 고유 edge 경로 23개(Ring 미경유 18개, Ring 경유 5개)여야 한다.
4. 사례 재현용 trace 도구를 준비한다. 경로·시작 차선·신호 offset을 지정하고 deterministic 정책으로 재생할 수 있어야 한다. 기록 항목은 step, 시각, edge, lane, 위치, 속도, 관측 벡터, 행동, 실제 차선 변경 여부, 신호 상태·거리, 보상 총합·성분, 종료 이유다. 보상 성분을 합칠 때 총 reward를 덮어쓰지 않는다.
5. offset 분리·출발 차선 일치·출력 경로 분리를 검증하는 작은 테스트를 실행한다. 기존 모델로 소수 사례 재생도 확인한다. 이 단계에서 모델 후보를 고르기 위해 holdout 전체를 반복 사용하지 않는다.

평가 코드 준비가 끝나면 커밋과 변경 파일을 기록하고 실험 동안 동결한다. 저장 설정을 읽더라도 평가기의 환경 구현은 현재 checkout 코드를 사용할 수 있으므로, 평가 코드 버전도 반드시 기록한다.

## 4. 새 학습 실행

프로젝트 루트의 SUMO·PyTorch 설치 환경에서 실행한다. 아래는 PowerShell 명령이다. 우선 seed 0을 완료하고 결과를 보존한 다음 `$trainSeed`를 1, 2로 바꾸어 순서대로 실행한다. GPU 학습 세 개를 동시에 시작하지 않는다.

```powershell
$trainSeed = 0
python train_parallel.py --phase 1 --num-envs 512 --num-workers 4 `
  --steps-per-env 64 --iterations 1920 --learning-epochs 10 --minibatch-size 1024 `
  --seed $trainSeed --randomize-departures True --eval-interval 0 `
  --lookahead-edges 3 --lane-decision-distance-scale 300 --lane-change-margin-scale 25 `
  --off-route-lane-penalty 0 --early-lane-change-bonus 0 --lane-keep-bias 0.5 `
  --target-kl 0 --signal-fine-distance-scale 0 --yellow-tracking-max-decel 0 `
  --red-park-penalty-coef 0.10 --red-speed-tracking-cap 0.40 `
  --legacy-red-speed-tracking --checkpoint-iterations 300 480 960 1920
```

실행 전에 `python train_parallel.py --help`로 옵션을 확인한다.

- 콘솔의 결과 폴더를 seed별 실행 목록에 기록하고 stdout/stderr도 보존한다.
- 최종 설정과 관측 차원, 초기화 방식, 총 학습량이 위 표와 맞는지 확인한다.
- 실행 중단 시 저장된 `model.pt`가 완료 모델이라는 보장은 없다. 로그의 완료 iteration과 경험 수로 판정한다.
- `--init-model`은 가중치 초기화 기능이다. optimizer·환경·난수 상태를 포함한 정확한 재개로 취급하지 않는다.
- 기본 계획은 정식 학습 3회다. 성능 실패를 이유로 추가 seed·보상 탐색·학습 연장을 하지 않는다. 인프라 오류 시 원인을 고치고 해당 seed를 처음부터 한 번 재시도할 수 있으며, 전체 시도는 최대 4회로 제한한다. 반복 오류로 완료하지 못하면 미완료 사유와 증거를 보고한다.
- 한 seed가 성능 기준에 실패해도 나머지 seed는 동일 조건으로 완료한다. 그래야 재현성 실패 범위를 알 수 있다.

## 5. 모델별 평가 실행

최종 iteration 1920 모델을 사전에 정한 평가 대상으로 사용한다. 중간 체크포인트는 학습 경향 진단용이다. 평가 결과가 좋은 체크포인트로 최종 모델을 바꿔치기하지 않는다.

```powershell
$run = 'results/parallel_1_새로운실행폴더'
Get-FileHash -LiteralPath "$run/model.pt" -Algorithm SHA256

# 3절의 옵션 확장을 완료한 뒤 실행한다.
python scripts/evaluate_quick.py $run --num-workers 4 --offset-set development
python scripts/evaluate_quick.py $run --num-workers 4 --offset-set holdout
```

세 모델 모두 동일한 평가 코드·평가 seed·경로·출발 차선·offset 목록을 사용한다. 총 **3개 모델 × 2세트 × 1,150 = 6,900 episode**다. 기존 비교 모델의 평가는 이 수에 포함하지 않는다.

세트마다 `route_evaluation.csv`, `evaluation_summary.json`, `learning_curve.png`를 보존한다. JSON의 모델 SHA256이 실제 파일과 일치해야 한다. 반복 실행으로 이전 결과를 덮어쓰기 전에 별도 경로에 보존한다.

동결된 세 모델을 선택한 뒤 holdout을 한 번씩 평가한다. holdout 결과를 보고 설정을 바꾸면 그 세트는 더 이상 미사용 검증 세트가 아니다. 변경 실험에는 새로운 검증 세트를 정해야 한다.

## 6. 이번 실험의 통과 기준

다음은 이번 검증을 위해 사전에 정한 프로젝트 기준이며, 외부의 공인 안전 기준을 의미하지 않는다. 결과를 본 뒤 기준을 완화하지 않는다.

| 항목 | 모델별·평가 세트별 기준 |
|---|---|
| 데이터 무결성 | 정확히 1,150행, 경로별 50개, 중복·누락 0 |
| 완주 | **1,150/1,150, 모든 경로 50/50** |
| 실패 | 충돌·적신호 위반·wrong lane·timeout·unknown 각각 0 |
| 최종 적신호 정차 거리 | 전체 중앙값 1.5~4m, P90 ≤ 5m |
| 최초 황·적신호 정차 거리 | 전체 중앙값 1.5~4m, P90 ≤ 5m |
| 정차 표본 | 위 두 지표 각각 전체 n ≥ 100. 경로별 n도 공개 |
| 청신호 재출발 | observed ≥ 100, no_restart = 0, 지연 P90 ≤ 2초 |

표본이 기준보다 적거나 값이 누락되면 통과로 간주하지 않고 해당 항목을 **판정 보류**로 남긴다. 신호 정차가 없는 경로의 거리 값이 null인 것은 그 자체로 실패가 아니다. 정차 표본이 10개 이상인 경로는 경로별 중앙값·P90도 확인하고, 전체와 같은 거리 기준을 벗어나면 해당 항목을 실패로 판정한다. 그 미만은 원시 표본과 표본 수를 공개하고 사례 추적으로 보완한다.

`red_wait_clearance_m`은 episode의 마지막 측정 가능한 적신호 정차 상태이고, `first_signal_stop_clearance_m`은 첫 황·적신호 정차 상태다. 둘 다 모든 신호 접근·정차를 빠짐없이 측정한 지표가 아니다. `green_restart` 역시 대표적인 첫 관측 사건을 추적하며 모든 신호의 재출발을 보장하지 않는다. **요약 통계만으로 행동 검증을 완료하지 않는다.**

최종 판정은 6개 결과 행 모두 기준을 통과하고 아래 사례 검토를 완료했을 때만 `Phase 1 검증 통과`로 한다. 0건의 관측 실패가 실제 모든 상황에서의 무실패를 증명하는 것은 아니다.

## 7. 사례 추적과 실패 분석

각 모델·세트에서 아래 사례의 합집합을 추적한다. 같은 사례는 중복 재생하지 않아도 된다.

- 실패 episode 전부를 목록화한다. 재생은 `(경로, 시작 차선, 종료 이유)`별 대표 1개씩 수행하고, 같은 그룹에 다른 증상이 있으면 추가한다. 모든 실패를 재생했다고 과장하지 않는다.
- 최초 정차 거리가 가장 큰 3개, 마지막 적신호 정차 거리가 가장 큰 3개, 재출발이 가장 늦은 3개.
- Ring 5개 경로에서 각각 적어도 1개 사례. 필요한 차선 변경을 언제 명령했고 실제로 언제 수행했는지 확인한다.

확인 질문:

1. 멀리 정차했다가 나중에 접근해서 마지막 정차 통계만 좋아진 것은 아닌가?
2. 적신호 정차 중 반복적인 출발·정지를 하거나 정지선을 침범하는가?
3. 청신호 이후에도 정차하거나 불필요하게 브레이크를 유지하는가?
4. Ring 진입 전에 차선 준비를 실패했는가, 진입한 뒤 잘못 나갔는가?
5. 잘못된 명령을 내린 것인가, 올바른 명령이 안전 게이트에 거절된 것인가?

보고서는 관측 사실, 가능한 원인, 추가 증거가 필요한 가설을 구분한다. 평균 보상이나 변경 확률 하나만으로 원인을 단정하지 않는다. 사례 추적에서 명백한 조기 정차·재출발 실패·차선 선택 문제가 확인되면 통계 통과와 별개로 행동 검증 실패로 기록한다.

## 8. 최종 산출물과 완료 조건

`docs/phase1_retraining_validation_report.md`에 다음 내용을 작성한다.

1. 세 seed의 새 run 경로, 코드 커밋, 실행 명령, 모델 SHA256, 실제 경험 수, 완료 여부.
2. 기존 비교 모델과 새 run의 설정 차이. seed 외 차이가 있으면 같은 조건 재현의 성립 여부를 명시한다.
3. seed별·세트별 6행 요약표: 완주 수, 종료 이유별 횟수, 최초/최종 정차 n·중앙값·P90, 재출발 observed·no_restart·P90, 통과/실패/보류.
4. 경로별 결과와 실패 사례 목록, 대표 trace 경로 및 관측 근거.
5. 세 run의 학습 곡선과 중간 체크포인트 진단. 최종 모델 선택 기준은 변경하지 않는다.
6. 기존 seed 0 모델과 새 seed 0의 비교가 필요하면 동일 평가기로 별도 평가한다. 동일 seed라도 장치·라이브러리·코드 차이로 가중치나 결과가 완전히 같지 않을 수 있으므로 SHA 일치 자체를 성능 통과 조건으로 두지 않는다.
7. 최종 결론: `통과`, `성능 미달`, `검증 미완료` 중 하나와 항목별 근거. Phase 2 진입은 통과 이후의 별도 작업으로 남긴다.

완료 체크리스트:

- [ ] 평가 도구를 준비·검증하고 코드 버전을 동결했다.
- [ ] seed 0·1·2를 모두 새로 학습했다. 미완료는 이유와 로그가 있다.
- [ ] 완료 모델의 6개 평가 결과와 모델 해시를 보존했다.
- [ ] 정차·재출발 표본과 경로별 취약점을 확인했다.
- [ ] 사례 추적과 최종 보고서를 작성했다.
- [ ] 성능 실패를 숨기기 위한 재학습·모델 선택·기준 변경을 하지 않았다.

성능 미달도 위 증거를 갖춰 보고하면 검증 작업 자체는 완료할 수 있다. 다만 **검증 작업 완료와 Phase 1 성능 통과는 반드시 구분한다.**
