# 데이터 컬럼 설계 근거

[data_columns_submission.md](data_columns_submission.md)의 표에 대한 설명이다. 기준 코드는 BC 브랜치(`7a6c4b6`, BC49 기준 모델)다.

## 설계 원칙 (교수님 피드백 반영)

- 값은 가능한 한 숫자로 둔다. 신호는 문자(`r`/`y`/`G`) 대신 적=0, 황=0.5, 녹=1로 저장하고 방향별로 차원을 나눈다.
- 겹치거나 다른 컬럼으로 계산되는 정보는 저장하지 않는다.
- `state`만으로 도로 구성과 신호 상황을 알 수 있어야 한다. 이 기준은 정책 observation이 아니라 `state`에 적용한다.

비보호 유턴 구현 및 전용 상호작용 후보 분석은 제외한다. 기존 신호제어 유턴 경로(중앙 A1·A3, 상류 A2·A5)와 일반 주행 분석용 차량 Route 정보는 유지한다.

## observation 49차원 세부

- 0–30번은 −1~1로 자른다. 31–48번의 거리 항목은 자르지 않으므로 1을 넘을 수 있다.
- 주변 차량 거리는 50m 범위의 실제 범퍼 사이 거리다. 앞차가 없으면 `[1, 1]`, 뒤차가 없으면 `[-1, -1]`이다.
- 차로 연결성은 없음 −1, 이어짐 1, 50m 안에서 끝나면 남은 거리/50이다. 예정 경로와 무관한 물리적 연결이다.
- 신호는 전방 100m 안에서 가장 가까운 제어 신호다. 없으면 네 값 모두 0이다. `G`와 `g`를 구분하지 않는다.
- 도로 분기 각도는 양수가 왼쪽이다. 안내가 없으면 해당 네 값은 0이다.
- 자차가 사라진 행(충돌·도착 직후)은 49개 모두 0이다.

### 이전 Phase 1 관측(51-dim)에서 뺀 항목

| 이전 항목 | 처리 | 이유 |
|---|---|---|
| 차로 9개 경로 연결성 + 차로 9개 앞 3개 도로 연결성 (18칸) | 차로 5개 물리적 연결성(5칸) + 도로 분기 안내(8칸)로 대체 | 같은 차로를 두 기준으로 중복 표현했고, 차로 수도 다른 블록(5개)과 달랐음 |
| 신호 "없음" one-hot 칸 | 삭제. 신호가 없으면 네 값 모두 0 | "없음"과 "거리=1"이 같은 정보를 두 번 표현 |
| 진출 제한 지점 거리, 차로 변경 여유 | 삭제 | 도로 분기 안내와 겹침 |
| 목적지 one-hot | 삭제 | 도로 분기 안내가 진행 방향을 전달 |

## `all_signals`를 진입로 5칸으로 두는 이유

신호 계획은 한 번에 한 진입로만 녹색이다(A1→A2→A3→A4→A5, 녹 20s·황 3s·전적 2s). 같은 진입로의 연결은 항상 같은 색이고, 상류 U턴 2곳(A2, A5)도 해당 진입로의 중앙 신호를 따른다. BC 지도를 생성해 확인한 결과, 중앙 제어기 `nC`의 연결 28개가 모두 자기 진입로의 녹색 현시에서만 녹색이다. 따라서 5칸으로 손실 없이 표현된다. 전적색 구간은 5칸 모두 0이다.

자차가 사라진 뒤에도 `all_signals`와 `signal_remaining_s`는 계속 기록한다. 조회에 실패하면 둘 다 null이다. 신호 계획을 진입로별 동시 신호가 아닌 방식으로 바꾸면 연결별 칸으로 늘린다.

## 양보형 녹색(`g`)을 구분하지 않는 이유

BC 지도에서 `g`는 U턴 연결 4개에만 나온다.

| `nC` 연결 | 진입 차로 → 진출 도로 |
|---|---|
| 13 | A3_in 4번 → A3_out (중앙 U턴) |
| 20 | A1_in 4번 → A1_out (중앙 U턴) |
| 26 | A2_in1 3번 → A2_out1 (상류 U턴) |
| 27 | A5_in1 2번 → A5_out1 (상류 U턴) |

이전 Phase 1 지도에서 `g`였던 A1_in → A5_out 합류 연결은 BC 지도에서 삭제됐다.

1. **매 step 바뀌는 정보가 아니다.** 신호 생성 코드가 U턴 연결(`dir="t"`)에 고정으로 `g`를 부여한다. 매 행에 저장하면 같은 정보가 반복된다.
2. **비보호 유턴이 없다.** 중앙 U턴이 녹색일 때 마주 오는 흐름은 적색이다. 남은 양보 상황은 상류 U턴이 같은 도로의 진출 차량과 합류하는 경우 정도이며, 연결의 고정 속성이다.
3. **정책 관측도 구분하지 않는다.** observation 31–34번은 `G`와 `g`를 모두 녹색으로 본다.

필요하면 지도의 `dir="t"`로 양보형 연결을 찾는다. 비보호 유턴을 도입하면 다시 검토한다.

## 의미가 바뀐 기존 컬럼 세부

- `reward`: 적신호 정차 보상은 정지선과 앞차 대기열 중 가까운 쪽까지의 여유를 기준으로 한다. 실제 계수는 `metadata.json`의 보상 설정을 따른다.
- `event.collided`: 자차와 배경차 모두 범퍼 사이 0.2m를 충돌 기준으로 쓴다. 추종 모델의 `minGap`과는 별개다.
- `event.lane_before`, `event.lane_after`: 0이 가장 오른쪽 차로다. 자차가 사라진 행은 빈 칸이다.

## 충돌 상대 정보를 저장하는 이유

- 환경은 SUMO를 `--collision.action remove`로 실행한다. 충돌하면 자차와 상대 차량이 그 step에 함께 제거되므로 `next_state`에는 상대 차량이 없다. `state`(t 시점)의 주변 차량 중 누구와 부딪혔는지는 나중에 거리로 추측할 수밖에 없다.
- 기존 충돌 판정은 `getCollidingVehiclesIDList()`로 자차 포함 여부만 확인한다. 충돌 step에서 `simulation.getCollisions()`를 함께 호출하면 가해·피해 차량 ID, 차량 종류, 속도를 정확히 얻는다. 충돌이 없는 행에는 추가 비용이 없다.
- `failure_reason = 1`(충돌)을 자차의 추돌(제동 실패)과 피추돌(배경 차량 원인)로 나누고, 차량 종류별 충돌 경향을 볼 수 있다.
- `ego_is_collider`는 SUMO의 collider(뒤에서 들이받은 차량)가 자차인지로 정한다.
- 상대 차량의 차로·위치는 `state.vehicles[]`에서 ID로 찾을 수 있어 따로 저장하지 않는다. 자차 속도도 `state.ego_speed`에 있다.

**SUMO 충돌 유형(`collisionType`)은 저장하지 않는다.** 교차로 충돌 검사(`--collision.check-junctions`)가 꺼져 있고 차로 변경이 순간 이동 방식이라, 유형이 사실상 항상 같은 차로 추돌(`collision`)로 나온다. 충돌 직전 차로 변경 여부는 같은 행의 `action.lane_change_applied`로 확인한다. 교차로 충돌 검사를 켜면 유형 저장을 다시 검토한다.

배경 차량 전체의 종류(`state.vehicles[].type`)는 저장하지 않는다. 분석에 필요한 경우는 충돌 상대뿐이므로 `collision_partner_type`으로 충분하다.

## 신규·후처리 컬럼 세부

- `event.red_light_violation`은 같은 step에 적신호 통과 후 자차가 사라지면 검사하지 못해 false일 수 있다. 황색 통과는 위반이 아니다.
- `event.wrong_lane`은 원인 불명 소실도 포함하므로 차로 오진입률을 이것만으로 단정하지 않는다.
- `failure_reason` 우선순위: 적신호 위반(2) → 충돌(1) → 정상 도착(0) → 원인 불명 소실(5) → 차로 실패(3) → 시간 초과(4).
- 배경 차량 Route ID는 에피소드마다 재사용될 수 있으므로 같은 `episode`의 `new_routes`로 경로를 찾는다.

## `state` 충분성 점검

| 알아야 할 것 | 사용하는 컬럼 |
|---|---|
| 자차가 있는 도로·차로 | `state.ego_road_id`, `state.ego_lane_id`, `state.ego_lane_pos` |
| 도로의 차로 수·연결·형상 | 위 ID + `.sumo/highway.net.xml` |
| 앞으로 지날 도로 | `episode_info.route_id` + `new_routes` |
| 지도 전체 신호와 전환 시점 | `state.road_context.all_signals`, `state.road_context.signal_remaining_s` |
| 주변 차량 위치·차로·경로 | `state.vehicles[]` (`lane_id`, `lane_pos`, `speed`, `route_id`) |

차로 수 같은 고정 지도 정보는 ID로 조회할 수 있어 매 행에 넣지 않는다.

## 저장하지 않기로 한 항목

| 항목 | 이유 |
|---|---|
| `state.road_context.observed_signals[]` | 색과 정지선 거리는 observation 31–34번에, 지도 전체 신호는 `all_signals`에 있음. 신호 문자가 String이기도 함 |
| `tls_id`, `program_id`, `phase_name`, `phase_index`, 연결별 신호 문자열 | 제어기가 `nC` 하나이고 프로그램이 고정이라 매 행 같은 값이거나 `all_signals`와 같은 정보. 대부분 String |
| `state.road_context.sim_time_s` (매 행의 SUMO 시각) | 신호는 `all_signals`로 기록하므로 시각으로 계산할 필요가 없고, 수집기가 SUMO 로그 파일을 저장하지 않아 시각으로 맞춰 볼 대상도 없음 |
| `episode_info.sim_time_start_s` (기록 시작 시점의 SUMO 시각) | 위와 같은 이유. 재현은 `seed`·`sumo_seed`와 설정으로 충분함. SUMO 출력 파일을 함께 저장하게 되면 다시 추가 |
| `episode_info.signal_offset_s` (시작 시점의 신호 주기 내 위치) | t=0 행의 `all_signals`·`signal_remaining_s`로 계산. 예: `[0, 1, 0, 0, 0]`, 15초 남음 → A2 녹색(주기 25초 지점 시작)이 5초 지남 → 30초 |
| 양보형 녹색 구분 값 | 위 절 참고 |

## 현재 구현 상태

이 설계는 아직 수집 코드와 기존 데이터에 반영되지 않았다. 현재 `data/nohyeong_phase1.*`은 Phase 1 모델의 51-dim 관측과 `observed_signals`를 담고 있다. 이 설계대로 수집하려면 BC49 모델로 다시 수집하고, 수집 코드에서 `observed_signals`를 `all_signals`·`signal_remaining_s`로 바꾸고, 충돌 step에 `getCollisions()` 결과로 `event.collision_*`·`event.ego_is_collider`를 채워야 한다.
