# 데이터 컬럼 팀원 피드백 및 답변

| 팀원 피드백 | 답변 |
|---|---|
| **event.collision_partner_id**<br>개인적으로 int를 사용했으면 하는데<br>또 int로 사용할 경우 차량 구분이 힘들기 때문에 string도 나쁘지는 않지만 string을 어떻게 설정할지를 정해야할 것 같습니다. (state.vehicles[].route_id와 비슷한 방식으로 정하면 좋을 것 같습니다.)<br>예시) A2 -> A3으로 가는 51번째 차량: A2_00051_A3 | String으로 유지하겠습니다. SUMO가 차량에 붙이는 ID가 원래 제안해 주신 방식과 같은 형식이라 그대로 쓰기로 했습니다.<br>예시) A2 → A3로 가는 51번째 차량: f_A2_A3.51 (원형 도로를 지나는 차량은 lf_RING_A1_A3.7 형식)<br>state.vehicles[].id와 같은 값이라 충돌 상대 차량을 바로 찾을 수 있습니다. 노션에 ID 규칙 추가하였습니다. |
| **state.road_context.signal_remaining_s**<br>제가 이해한 것이 맞다면 지금 진행 중인 신호 단계가 끝날 때까지 남은 시간인 것으로 보이는데 그렇다면 이것도 그냥 state.road_context.all_signals와 같이 수집하여 int[] 형식으로 수집하는게 좋지 않을까요? | 이해하신 게 맞습니다! 지금 진행 중인 신호 단계가 끝날 때까지 남은 시간입니다. 중복을 최소화하기 위해 모든 진입로의 남은 시간을 따로 기록하지 않고, 현재 진행 중인 단계의 남은 시간 하나만 기록하려고 합니다. 신호가 A1 → A5 순서로 녹색 20초, 황색 3초, 전적색 2초씩 고정으로 돌기 때문에, 이 값 하나만 있으면 다른 진입로가 언제 바뀌는지는 계산할 수 있습니다.<br>예시) A2 녹색이 15초 남았다면 A3 녹색은 15 + 3 + 2 = 20초 뒤<br>그리고 0.5초 단위로 기록되는 값이라 int로 하면 0.5초가 잘려서 Float로 두었습니다. |
| **terminated**<br>이거 자체가 이상하다기 보다는 종료되는 경우의 수가 `충돌, 도착, 적신호 위반, 경로 밖 차로 끝에 정지, 자차 소실` 총 5개인데 boolean 보다는 int로 설정하고, event.collided 나 다른 항목을 제거해도 괜찮지 않을까요?<br>물론 데이터가 너무 하나에 모여있으면 구분하기 어려우니 나누는 편이 더 좋을 수도 있습니다.<br>이건 취향차이 일 것 같아요.<br>지금 문서에 event 항목이 딕셔너리로 저장되는 것으로 보이는데 각각의 항목이 좀 여러곳에 퍼져있어서 각각의 관계를 잘 모르겠습니다. 따라서 저나 다른 사람이 판단하기보다는 승준님이 판단해주시는게 좋을 것 같습니다. 항목의 관계성을 보고 유지할지 terminated로 합칠지 결정해주시면 될 것 같습니다. | 교수님 기본 칼럼이라 Boolean으로 유지하겠습니다. event.collided, event.arrived도 기본 칼럼이라 남겨두었습니다. 대신 말씀해 주신 대로 항목들 관계가 흩어져 있어서, 충돌, 도착, 적신호 위반 같은 종료 상황마다 terminated, truncated, event 항목들이 어떤 값이 되는지 한 표로 정리했습니다. 종료 원인을 숫자 하나로 보고 싶을 때는 후처리 칼럼 analysis.failure_reason을 쓰면 됩니다. 노션에 표 추가하였습니다. |
| **event.lane_before, event.lane_after**<br>어떤 걸 의미하는지 잘 모르겠습니다. 혹시 차로(또는 차로 변경)에 관한 데이터 인가요? | 행동 전후 자차의 차로 번호입니다(0이 가장 오른쪽 차로). 두 값이 다르면 해당 스텝에 차로 변경이 일어났다는 것을 알 수 있습니다! 노션에 설명 추가하였습니다. |
| **episode_info.seed sumo_seed**<br>모든 차량이 같지 않나요? | 맞습니다! 차량별 값이 아니라 에피소드 하나에 하나인 값이라 한 에피소드 안의 모든 차량이 같습니다. 그래서 에피소드 첫 행에만 기록합니다. seed는 자차 경로를 뽑는 데, sumo_seed는 SUMO가 배경 차량 쪽 무작위 요소를 정하는 데 쓰입니다. 두 값을 같게 주면 같은 에피소드를 재현할 수 있습니다. 노션에 설명 추가하였습니다. |
| **episode_info.sim_time_start_s**<br>기록 시작 시뮬레이션 시각이 무슨 항목인가요? 자차의 출발 시간을 sim이 감지한 시간인가요? | 원래 신호를 1인칭으로 기록할 때 전체 신호를 계산하려고 넣었던 값인데, 이제 3인칭으로 모든 신호를 직접 기록해서 불필요할 것 같아 삭제하였습니다.<br>참고로 의미는 맞게 이해하셨습니다! |
| **episode_info.signal_offset_s**<br>마찬가지로 잘 모르겠습니다. 신호를 쓰지 않는 실행? 시작 시점의 신호 주기 내 위치? 제가 이해한게 맞다면 차라리 차가 출발했을 때의 시간을 기록하는 것이 좋지 않을까요?(제가 잘못 이해한 걸 수도 있어요) | 에피소드가 신호 주기(125초) 중 몇 초 지점에서 시작했는지를 나타내는 값이었습니다. 매번 A1 녹색부터 시작하면 같은 신호 상황만 겪게 돼서, 에피소드마다 신호 시작 지점을 다르게 맞추고 그 위치를 기록한 것입니다. 그런데 지금은 매 행에 all_signals와 signal_remaining_s가 있어서 첫 행 값으로 계산할 수 있는 중복 칼럼이 됐습니다. 그래서 삭제하였습니다.<br>말씀하신 출발 시간은 신호 시작 지점을 따로 맞추기 때문에 신호 상태를 알려주지 못해서, 대신 쓰기는 어렵습니다. |
| **후처리 칼럼**<br>후처리 칼럼부분은 데이터 수집 후 나중에 따로 계산하는것도 가능하니 이건 일단 정리만 해주세요.<br>근데 우리가 수집한 데이터 칼럼에서 analysis.merge_diverge_distance 가 나중에 계산이 가능한지 모르겠습니다. | 수집 후 계산 가능합니다! 매 행의 자차 위치(state), 자차 경로 전체(new_routes), 지도 파일(.sumo/)이 모두 저장되기 때문에, 경로를 따라 다음 합류·분기 지점까지 거리를 더하면 됩니다. 후처리 칼럼은 말씀하신 대로 일단 정리만 해두었습니다. |
