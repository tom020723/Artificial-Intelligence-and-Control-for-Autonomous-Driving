# 신호 대응 모델 개선: 후속 에이전트 작업 지침

작성일: 2026-11-13. 확인한 기준 브랜치: `parallel_train`, commit `1b8fb31`.

## 1. 맡길 목표

**신호가 작동하고 배경차가 없는 환경에서, 중앙 차선으로 출발하는 PPO 모델을 개선하여 아래 성능 기준을 학습 seed 3개에서 각각 달성하고 재현 가능한 결과 묶음을 남긴다.**

환경 실행 확인, 문서 수정, 학습 한 번 완료, 누적 보상 상승만으로 작업을 완료하지 않는다. 실패 사례 분석 → 한 가지 변경 → 재학습 → 같은 평가 비교를 반복한다. 성능 목표는 이번 작업을 위한 제안 기준이며 기존에 달성됐다는 뜻이 아니다.

이번 범위는 신호 대응의 기준 모델 확립이다. 배경차 학습, 도로 변경, 새로운 RL 알고리즘 도입은 범위 밖이다. 랜덤 차선 출발은 마지막 진단 평가까지만 수행하고, 그 성능 개선은 다음 작업으로 남긴다.

## 2. 현재 상황: 반드시 먼저 이해할 것

| 항목 | 현재 의미 |
|---|---|
| 현재 `train_parallel.py --phase 1` | 정상 신호 + 배경차 없음 |
| 현재 `--phase 2` | 정상 신호 + 배경차 교통량 커리큘럼 |
| 과거 `docs/train.md`의 Phase 1 | 항상 초록불 + 배경차 없음. 현재 Phase 1과 다름 |
| 과거 `parallel_1_20261110_194551_441463` | 항상 초록불에서 학습한 모델. 현재 신호 대응의 성공 근거로 사용하지 않음 |
| 현재 보상 | `train.py`의 `REWARD` 위에 `train_parallel.py`의 `SIGNAL_STOP_REWARDS`를 덮어씀 |
| 현재 관측 | 병렬 실행에서 49차원, 목적지 one-hot 없음, 신호 1개 |
| 기존 빠른 평가 | `scripts/evaluate_quick.py`: 27개 경로 × 신호 시작 offset 50개 = 1,350회 |

`train.md`의 301,056 step, 보상표, Phase 번호를 현재 병렬 설정으로 간주하지 않는다. 현재 보상에는 적신호 목표 속도 추종, 안전 구역 정차, 초록불 정차 감점 등이 이미 있다. 새 보상을 추가하기 전에 기존 항의 실제 값을 확인한다.

다른 브랜치의 lane-brake 개선은 검증할 후보일 뿐이다. 필요하면 먼저 이력과 차이를 읽고, 타인 브랜치를 채택할 때는 AGENTS.md에 따라 merge로 이력을 보존한다. 다른 브랜치를 통째로 바꿔 끼워 실험 조건을 동시에 변경하지 않는다.

## 3. 합격 기준

### 3.1 고정할 평가 조건

- 경로: 기존 직접 경로 22개 + Ring 경로 ID 5개. 중복 edge 경로가 있어도 기존 27개 ID를 유지한다.
- 출발: 경로별 중앙 차선, 기존 출발 속도. 배경차 0.
- 신호: 기존 125초 주기와 phase 지속 시간, 제어 주기 0.5초 유지.
- 행동: deterministic 정책. 평가 때 확률적으로 차선을 뽑아 성능을 올리지 않는다.
- 개발 평가: 기존 `evaluate_quick.py`의 offset 1.0, 3.5, …, 123.5초, 총 1,350회.
- 최종 별도 평가: offset 2.0, 4.5, …, 124.5초, 같은 경로로 총 1,350회. 기존 코드에 없으면 offset 선택 옵션을 추가한다. 기본 개발 평가 목록은 변경하지 않는다.
- 두 offset 집합은 같은 신호 주기의 서로 다른 시작 시점이다. 새로운 주기 길이나 새로운 도로에 대한 일반화라고 표현하지 않는다.

### 3.2 최종 설정의 학습 seed 0, 1, 2가 각각 만족할 기준

아래 기준을 개발 평가와 최종 별도 평가에서 **각각** 만족해야 한다. 세 모델의 평균으로 실패한 seed를 숨기지 않는다.

| 지표 | 합격 기준 |
|---|---|
| 전체 도착 | 1,350회 중 1,337회 이상, 약 99% 이상 |
| 적신호 위반 | 0회 |
| 충돌 | 0회 |
| unknown 또는 분류 누락 | 0회, 모든 에피소드가 한 종료 원인으로 집계 |
| 경로별 도착 | 27개 경로 각각 50회 중 48회 이상 |
| 적신호 정차 여유 거리 | 아래 정의로 중앙값 3~8m, p90 ≤ 15m |

정차 거리 지표는 에피소드별 `red_wait_clearance_m`의 유효 표본을 사용한다. 기존 구현이 어떤 정차 시점을 대표값으로 고르는지 `utils/evaluator.py`를 읽어 보고서에 적는다. 유효 표본 수, 전체 대비 비율, 경로별 표본 수를 함께 기록한다. 정차가 없다고 0m로 대체하거나, 먼 정차 표본을 버리지 않는다. 전체 유효 표본이 100개 미만이면 정차 품질은 **검증 부족**으로 처리하고 합격시키지 않는다. Ring처럼 신호 대기가 없는 경로에 표본을 강제하지 않는다.

기존 요약에 p90이 없으면 원시 CSV의 동일 지표에서 계산한다. 잘못된 집계가 발견되면 수정 전후를 기록하고 비교 대상 전체를 같은 집계로 재평가한다.

## 4. 첫 작업: 실행과 재현 조건 확정

1. `git status`, 현재 branch/commit, AGENTS.md를 읽는다. 사용자 변경을 덮어쓰지 않는다. 현재 기준과 코드가 달라졌으면 차이를 기록한다.
2. Python 실행 경로, Python/PyTorch/SUMO/libsumo 버전, CPU/GPU, 실행 OS를 기록한다. 사용 가능한 기존 환경부터 확인한다.
3. 로컬 `results/`에서 현재 정상 신호·무배경차 설정의 모델을 찾는다. 폴더 이름 대신 저장 설정과 `parallel_config.json`을 확인한다. 미추적·이전 브랜치 잔여 파일과 현재 Git 제공 자료를 구분한다.
4. 각 후보의 모델 SHA256, 실제 학습 step, 학습 seed, 초기 모델, 관측·보상·신호·출발 설정을 표로 만든다. 출처가 불명확한 모델은 참고용으로만 평가한다.
5. 새 장기 학습 전에 작은 환경 수로 1~2 iteration과 소수 평가 사례를 실행해 학습→저장→로드→평가가 연결되는지 확인한다. 이 결과를 성능 달성으로 보고하지 않는다.
6. 최종 기준과 호환되는 기존 모델이 있으면 먼저 개발 평가한다. 없다면 아래 기준 학습을 실행한다.

### 재현성에서 특히 확인할 것

- 현재 평가기는 저장된 설정을 복원하지만 환경 클래스는 현재 checkout에서 import한다. 저장 설정만 같다고 저장 당시 구현까지 복원된 것은 아니다.
- 각 실험의 실행 코드 commit과 미커밋 diff를 보관한다. 비교 평가에는 공통 평가 조건을 사용하되 모델이 학습한 관측 변환을 정확히 사용한다. 관측 수정 모델에 이전 변환을 넣지 않는다.
- 기존 run의 설정 파일이나 모델을 수정해 새 실험처럼 만들지 않는다. 평가 도구에 명시적 override가 필요하면 새 옵션과 별도 출력 경로로 구현한다.
- 동일 모델·동일 평가를 두 번 실행했을 때 종료 결과가 같은지 한 번 확인한다. 다르면 원인을 해결하기 전 성능 비교를 중단한다.
- 현재 학습 CLI에는 `--seed`가 없다. 반복 학습 전에 `--seed` 옵션을 추가하여 정책 초기화, 환경 난수, worker seed, JSON 기록에 일관되게 적용되게 한다. 기본값은 기존 HPARAMS seed를 유지한다. 다른 값이 로그에만 기록되는 구현을 금지한다.
- 학습 종료 시 평가 설정·실제 적용 보상·관측과 seed가 저장되는지 확인한다. 부모 모델을 사용하면 경로와 SHA256도 기록한다.

## 5. 기준 학습

다음 명령은 PowerShell에서도 실행 가능하게 한 줄로 적었다. 프로젝트 루트에서 실행한다.

```text
python train_parallel.py --phase 1 --num-envs 256 --num-workers 4 --steps-per-env 64 --iterations 500 --learning-epochs 10 --minibatch-size 512 --randomize-departures False --eval-interval 0
python scripts/evaluate_quick.py results/<실제_run_폴더>
```

- 총 8,192,000 transition이며 무작위 가중치에서 시작한다.
- `--seed` 구현 후에는 명령 끝에 `--seed 0` 등을 명시한다. 구현 전에는 이 옵션을 실행하지 않는다.
- 현재 Phase 1의 `--init-model`은 지원되지 않는다. Phase 2로 바꿔서 재학습을 이어가는 우회를 하지 않는다.
- 자원 부족 시 우선 worker 수를 4→2→1로 줄인다. 전체 환경 수와 rollout 크기는 유지한다. 환경 수까지 변경해야 하면 별도 기준 실험으로 기록하고 비교군도 같은 조건을 사용한다.
- 여러 장기 학습을 동시에 실행하지 않는다. 완료된 모델과 평가를 확인한 후 다음 실험을 시작한다.

## 6. 반복 개선 절차

### A. 기준 결과 만들기

기준 모델의 개발 평가를 실행하고 합격 기준과 비교한다. 실패 경로·offset·종료 원인 목록을 저장한다. 합격한다면 변경 없이 seed 재현 단계로 이동한다.

### B. 실패 원인 추적

가장 빈도가 높은 실패 유형에서 대표 사례 3개 이상을 추적한다. 실패 사례가 3개 미만이면 전부 추적한다. 종료 실패가 없어도 정차 거리 기준을 못 맞췄다면 가장 먼 정차 사례 3개를 추적한다.

각 사례에 다음 시계열을 CSV로 남긴다: step, route, edge/lane, 속도, 신호색, 정지선 거리, 경로 연결성 관측, 가속 명령, 차선 명령, 명령 수락 여부·거절 이유, 실제 차선 이동, 보상 항별 값, 종료 원인. 기존 info에 없으면 필요한 진단 출력을 추가한다. 수락된 차선 명령 횟수를 실제 차선 변경 횟수로 부르지 않는다.

### C. 한 가설만 변경

| 주된 증상 | 먼저 확인 | 변경 후보 |
|---|---|---|
| 잘못된 차선에서 정차·종료 | 목적 차선을 언제 관측할 수 있는가, 내부 차선 관측이 튀는가 | lookahead 범위 또는 내부 차선 관측 중 하나 |
| 빨간불에 너무 멀리 정차 | 목표 속도와 실제 속도, 속도 추종 보상, 정차 보상 활성 조건 | 관련 계수 하나 또는 해당 보상의 결함 수정 |
| 정지선 통과 위반 | 제동 시작 시점, 필요한 감속, 신호 판정 정확성 | 제동 유도 항 하나; 판정 버그면 먼저 별도 수정 |
| 초록불에도 계속 정차 | 신호 관측 전환, 가속 출력, 초록불 정차 감점 | 재출발 관련 항 하나 |
| 차선 명령 반복·왕복 | 명령 수락과 실제 이동 구분, 안전 게이트 거절 사유 | 관련 차선 항 하나 |

실험마다 실행 전에 `관측된 증상 → 원인 가설 → 변경 한 가지 → 개선을 기대하는 지표`를 적는다. 코드를 보기 전부터 보상 문제로 단정하지 않는다. 버그 수정은 보상 튜닝과 별도 실험으로 취급한다.

### D. 같은 예산으로 비교

- 후보는 우선 학습 seed 0, 동일한 8,192,000 step으로 비교한다.
- 학습 보상 상승만으로 채택하지 않는다. 개발 평가의 안전성과 도착률을 먼저 비교한다.
- 선택 순서: 위반+충돌 수 최소 → 전체 도착 수 최대 → 최악 경로 도착 수 최대 → 정차 p90 개선. 안전성이 나빠진 후보는 정차 거리가 좋아도 최종 후보로 삼지 않는다.
- 채택한 변경과 버린 변경을 모두 표에 남긴다. 한 번 실패한 조건을 기록 없이 다시 실행하지 않는다.
- 최고 모델은 별도 표시하여 보존한다. 가장 최근 모델을 자동으로 최고 모델로 지정하지 않는다.

## 7. 반복 횟수와 미달 처리

이번 한 차수는 **기준 설정 1개 + 변경 후보 최대 6개**를 seed 0에서 평가한다. 기준 설정이 이미 합격하면 불필요한 후보 실험은 생략한다. 최종 후보는 seed 1, 2로 추가 학습한다. 재현 검증에 실패하면 남은 후보 횟수 안에서 가설을 수정하고, 최종적으로 선택된 동일 설정을 seed 0, 1, 2에서 다시 검증한다. 다른 설정의 seed 결과를 합치지 않는다.

장기 학습 총 실행 횟수는 이 차수에서 최대 12회로 제한한다. smoke 실행은 제외하되 시간과 오류는 기록한다. 이 숫자는 끝없이 튜닝하지 않기 위한 작업 범위이며, 12회를 반드시 채우라는 뜻이 아니다.

최종 별도 offset 평가는 설정을 선정한 뒤에만 실행한다. 그 결과를 보고 다시 튜닝했다면 해당 집합을 더 이상 별도 검증으로 부르지 말고, 사용하지 않은 0.5초 tick에서 새 검증 집합을 고정·기록한다.

횟수를 소진해도 목표를 못 맞췄으면 **미달**로 종료 보고한다. 실패 기준을 완화하거나 평가 사례를 제거하지 않는다. 최고 모델, 목표와의 수치 차이, 실패 추적, 다음에 검증할 가설 1~3개를 남긴다. 장기 학습을 실행할 수 없는 자원·환경 문제는 **진행 불가 사유와 재개 명령**을 남긴다. 이를 성능 목표 달성으로 표시하지 않는다.

## 8. 합격 후 마지막 진단

선정 모델 하나를 랜덤 출발 차선으로 추가 평가한다. 저장된 학습 설정은 변경하지 않고 평가 override를 사용한다. 기존 도구에 옵션이 없다면 추가한다. 경로·offset·출발 lane·seed를 결과에 기록한다.

이 결과는 중앙 차선 기준과 별도로 보고한다. 랜덤 차선 평가 1회는 모든 차선 조합의 전수 검증이 아니다. 성능이 떨어져도 이번 작업을 무제한 확장하지 말고 다음 작업의 기준 결과로 남긴다. 배경차 Phase 2 학습은 이번 차수에서 시작하지 않는다.

## 9. 산출물과 인계

작업 시작 시 `docs/phase1_progress.md`를 만들고 각 학습·평가가 끝날 때 갱신한다. 최소 항목:

```text
상태: 기준 확보 / 원인 분석 / 후보 실험 / seed 검증 / 별도 평가 / 달성 / 미달 / 진행 불가
현재 코드 commit 및 diff 위치:
Python 실행 경로와 도구 버전:
현재 실행 중인 명령, PID 또는 세션, 로그 경로:
완료한 장기 학습 수 / 12:
최고 후보와 모델 SHA256:
다음에 실행할 정확한 명령:
아직 해결되지 않은 사항:
```

최종 산출물:

1. `docs/phase1_experiment_report.md`: 실험별 변경, 학습 seed·step, 평가 수치, 채택 여부, 목표 달성표.
2. run별 모델, 적용 설정, 코드 출처, 정확한 학습·평가 명령, 원시 평가 CSV와 요약 JSON, 그래프.
3. 대표 실패 사례의 시계열과 분석. 해결된 경우 동일 조건의 개선 전후 비교.
4. 최종 동일 설정 seed 0/1/2의 결과와 별도 offset 평가 결과. 미달이면 수행한 범위만 정직하게 표시.
5. 랜덤 차선 진단 결과 또는 선행 목표 미달로 미수행했다는 이유.
6. `docs/train.md`와 `docs/parallel_train.md`의 현재 단계 정의·대표 모델·실행 명령·구현 상태를 갱신. 과거 결과는 과거 조건임을 표시하고 보존한다.

대형 복제 도로 XML을 무조건 Git에 추가하지 않는다. 핵심 설정·코드·결과와 재생성 명령으로 재현성을 확보한다. 모델을 저장소 밖에 보관한다면 위치·해시·접근 방법을 명시하고 로컬 경로만으로 팀원이 받을 수 있다고 가정하지 않는다.

## 10. 다음 에이전트에게 붙여 넣을 요청

> `docs/phase1_agent_handoff.md`를 읽고 목표를 수행해줘. 계획이나 smoke test만 하고 끝내지 말고, 현재 모델 조사 → 기준 평가 → 실패 추적 → 필요한 개선 실험 → 동일 설정 학습 seed 3개 검증까지 진행해줘. 이미 진행 기록이 있으면 `docs/phase1_progress.md`를 읽고 이어서 수행해줘. 한 번에 한 장기 학습만 실행하고 이 문서의 실험 한도를 지켜줘. 성능 기준을 바꾸지 말고, 미달이면 최고 결과와 다음 가설을 남겨줘. 작업 중 결과와 다음 실행 명령을 계속 기록해줘.
